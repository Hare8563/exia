# Producer Skill

このスキルは、ユーザーの曖昧なシーン依頼を受け取り、制作に必要な情報を引き出してクリエイティブブリーフ（設計仕様書）を作成します。その後、各専門エージェントへの指示出しとパイプライン管理を担います。

## 役割の定義

- **プランニング**: ユーザーの意図を深掘りし、シーンの核心を言語化する
- **オーケストレーション**: 各エージェントを適切な順序・タイミングで起動する
- **品質管理**: 最終出力がブリーフの意図を満たしているか確認する

プロデューサーは「何を作るか」を決める役割であり、「どう作るか」は各専門家に委ねる。

---

## Phase 1: プランニング（ブリーフ作成）

> **STOP**: ブリーフの作成は **1-3. 確認と承認** でユーザーのOKを得るまで開始してはならない。
> インタビューを省略・短縮してブリーフに進むことを禁止する。

---

### 1-1. インタビュー ラウンド1「シーンの核心」

ユーザーから以下の情報を収集する。**全項目が揃うまでラウンド2に進まない。**

| 項目 | 内容 | 未収集時の対応 |
|------|------|--------------|
| **シーンID** | 管理用の識別子（例：S_002） | ユーザーに提案して確認 |
| **登場キャラクター** | 名前・役割・関係性 | 必ず聞く |
| **シーンの状況** | 場所・きっかけ・開始状況 | 必ず聞く |
| **感情の核** | このシーンで描きたい感情の変化 | 必ず聞く |
| **語尾・口調** | キャラクター固有の話し方の特徴 | 必ず聞く（言語崩壊アーク設計に必須） |
| **禁止事項** | 避けたい表現・展開 | なければ「なし」と確認 |

---

### 1-2. インタビュー ラウンド2「技術仕様」

**ラウンド1が完了してから**ラウンド2に進む。各エージェントの実行に必要な技術情報を収集する。
**全項目が揃うまでブリーフ作成に進まない。**

#### 画像生成仕様（visual-engineer 向け）

| 項目 | 内容 | 未収集時の対応 |
|------|------|--------------|
| **LoRA名** | キャラクターごとの LoRA ファイル名 | **必須。不明ならユーザーに確認する** |
| **LoRA強度** | 各 LoRA の適用ウェイト（例：0.8） | 不明なら推奨値 0.8 を提案 |
| **ベースモデル** | 使用する画像生成ベースモデル名 | 不明ならユーザーに確認する |
| **外見プロンプト** | キャラの外見を表す英語タグ群 | LoRA名から推定できる場合は提案 |
| **衣装・初期状態** | シーン開始時の服装・状態 | ラウンド1の情報から補完して確認 |
| **背景・環境** | シーン背景の視覚的特徴 | ラウンド1のシーン状況から補完して確認 |

#### 音声生成仕様（voice-sound-designer 向け）

| 項目 | 内容 | 未収集時の対応 |
|------|------|--------------|
| **RefWavパス** | キャラクターごとの参考音声ファイルパス | **必須。不明ならユーザーに確認する** |
| **声のタイプ** | 音域・声質（例：高め・少し掠れた）| RefWavで代替できる場合はスキップ可 |
| **感情別RefWav** | 平常時 / 興奮時 / 絶頂時で分ける場合はパスを確認 | なければ単一RefWavで進む |

#### シナリオ・スクリプト仕様

| 項目 | 内容 | 未収集時の対応 |
|------|------|--------------|
| **分岐の有無** | 選択肢・フラグ分岐が必要か | なければ「なし」と明示 |
| **既存フラグ** | 連携する既存フラグ名 | なければ「なし」と明示 |
| **目標ライン数** | 希望する本文の規模 | デフォルト100〜120を提案 |

---

### 1-3. 確認と承認（ゲート）

ラウンド1・ラウンド2で収集した情報を**箇条書きでユーザーに提示し、承認を得る**。

```
以下の情報でブリーフを作成します。問題なければ「OK」と返答してください。

【シーン概要】...
【キャラクター】名前 / LoRA: xxx.safetensors / RefWav: /path/to/wav
【口調・語尾】...
【技術仕様】ベースモデル: xxx / 分岐: なし
【禁止事項】...
```

> ユーザーから修正・追加があれば反映し、再度提示する。
> **「OK」の確認が取れるまでブリーフを作成してはならない。**

---

### 1-4. ブリーフ文書の作成

**1-3 の承認後のみ**、`workspace/brief.md` を作成する。

```markdown
# Creative Brief: [シーンID]

## シーン概要
[1〜3文で核心を述べる。「何が起き、誰がどう変化するか」]

## 登場人物

### [キャラ名]
- **役割**: [主人公/ヒロイン等]
- **外見・衣装**: [外見の特徴・シーン開始時の服装]
- **口調・語尾**: [固有の話し方。言語崩壊アークの起点として使用]
- **感情の変化**: [開始状態 → 終了状態]
- **LoRA**: `[LoRAファイル名]` / 強度: [weight]
- **外見プロンプト（英語タグ）**: `[tag1, tag2, ...]`
- **RefWav（平常時）**: `[ファイルパス]`
- **RefWav（絶頂時）**: `[ファイルパス / なし]`

## 感情アーク
- **起**: [シーン開始時の状況・緊張感]
- **承**: [なし崩し的な侵犯の始まり]
- **転**: [理性崩壊の転換点]
- **結**: [余韻・賢者タイム]

## 演出方針
- **トーン**: [例：緊張感のある静寂→熱狂→静寂]
- **BGM指針**: [例：冒頭は無音、絶頂前後でアップテンポ]
- **背景・環境**: [視覚的な背景情報]
- **ベースモデル**: `[画像生成ベースモデル名]`
- **視点**: ゼロ人称（プレイヤー主観）を基本とする

## 技術要件
- **分岐**: [あり/なし、あれば内容]
- **フラグ**: [使用するフラグ名と条件 / なし]
- **目標ライン数**: [最低100〜最大120]

## 禁止事項
- [ユーザーが特に希望したこと、または避けたいこと / なし]
```

## Phase 2: オーケストレーション

ブリーフが完成したら、以下の順序で各エージェントを起動する。

### 起動順序

```
Step 1: scenario-writer を起動
  → 入力: workspace/brief.md
  → 出力待ち: workspace/scenario_draft.md

Step 2: プロデューサーがシナリオレビューを実施（最大3回リテイク）
  → PASS なら Step 3 へ
  → FAIL なら scenario-writer に差し戻し → Step 1 先頭へ

Step 3（並列）: visual-engineer と voice-sound-designer を同時起動
  → visual-engineer 入力: workspace/scenario_draft.md（字コンテセクション）
  → voice-sound-designer 入力: workspace/scenario_draft.md（台本セクション）
  → 出力待ち: workspace/cg_manifest.json, workspace/audio_manifest.json

Step 4: scripter を起動
  → 入力: workspace/scenario_draft.md + workspace/cg_manifest.json + workspace/audio_manifest.json
  → 出力: public/scenarios/[シーンID].json
```

### 各エージェントへの指示テンプレート

**scenario-writer への初回指示**
```
workspace/brief.md を読み込み、シナリオドラフトを workspace/scenario_draft.md として出力してください。
```

**scenario-writer へのリテイク指示**
```
workspace/scenario_draft.md を以下のレビュー指摘に基づいて改稿し、上書きしてください。

[レビュー結果をここに貼付]
```

**visual-engineer への指示**
```
workspace/brief.md と workspace/scenario_draft.md の「字コンテ」セクションを読み込み、画像を生成して
workspace/cg_manifest.json を出力してください。

ブリーフの「登場人物」セクションに記載された以下の情報を使用してください：
- LoRAファイル名・強度
- ベースモデル
- 外見プロンプト（英語タグ）
```

**voice-sound-designer への指示**
```
workspace/brief.md と workspace/scenario_draft.md の「台本」セクションを読み込み、音声を生成して
workspace/audio_manifest.json を出力してください。

ブリーフの「登場人物」セクションに記載された以下の情報を使用してください：
- RefWav（平常時・絶頂時）のファイルパス
- 口調・語尾の特徴（声演技の基準として使用）
```

**scripter への指示**
```
workspace/scenario_draft.md, workspace/cg_manifest.json, workspace/audio_manifest.json を読み込み、
最終シナリオJSONを public/scenarios/[シーンID].json として出力してください。
```

---

## Phase 2.5: シナリオレビュー（リテイクループ）

scenario-writer の出力後、スクリプターに渡す前に必ずこのフェーズを実施する。

### レビュー基準

`.agents/scenario-writer/resources/review.md` を読み込み、以下のチェックリストで評価する。

#### A. 禁止と侵犯の力学
- [ ] 第1幕に「社会的立場・理性」が明確に定義されているか
- [ ] 侵犯のトリガー（背徳感の発生点）が描写されているか
- [ ] 「日常的な場所が異界へ変容する」過程が段階的に描かれているか

#### B. 誘惑ロジック
- [ ] 言葉による合意（「いいよ」「しよう」）で行為が始まっていないか
- [ ] 視覚・触覚・嗅覚による「抗えない衝動」で理性が麻痺する描写があるか
- [ ] 「恥ずかしい（禁止）」と「触ってほしい（欲望）」の矛盾シグナルが存在するか

#### C. 不連続性から連続性へ
- [ ] 行為が進むにつれ、論理的な会話が感嘆符・断片的な呻きへ移行しているか
- [ ] 二人の境界が溶け合う（連続性）プロセスが描かれているか

#### D. テンションコントロール
- [ ] 絶頂に近づくにつれ一文が短くなり、読点が増えているか
- [ ] 記号が `…` → `っ` → `！` → `！！` の順で強度を上げているか
- [ ] 絶頂後に静寂と賢者タイムが描かれているか

#### E. 文章量・構成
- [ ] 本文のナレーション/ダイアログが合計100本以上相当か
- [ ] 1つの主要アクションに20〜30本以上費やされているか
- [ ] 「足踏み描写」（行為を進めず現在の快感に留まる静止テキスト）が3箇所以上あるか

#### F. ゲームメディア原則（メタタグ変換 / ラリー集中）

> **判定基準**: 視覚・聴覚情報が「地の文に残っている」ことがNG。メタタグに変換されていればOK。

- [ ] **表情・顔色・涙・赤面**が地の文にある場合、対応する `[FACE:]` または `[CG:]` タグが同行に存在するか（タグなし地の文描写は即FAIL）
- [ ] **声の震え・息遣い・喘ぎの強弱**が地の文にある場合、`[VOICE:]` タグに変換されているか
- [ ] **雰囲気・静寂・空気感**が地の文にある場合、`[BGM:]` タグに変換されているか
- [ ] 地の文の主成分が「触覚・嗅覚・内面独白・認知的ギャップ」になっているか
- [ ] 連続する5本以上のナレーション（ノンダイアログ）ブロックが存在しないか
- [ ] 1つの感情フェーズ内で「ダイアログ ↔ ダイアログ ↔ モノローグ」のラリーが成立しているか

#### G. ブロック構造・数値的制約の遵守

- [ ] 地の文が **3行以上連続している箇所** がないか（あれば即差し戻し）
- [ ] ダイアログが **6本未満で途切れているセット** がないか（ラリーが短すぎる）
- [ ] 地の文が「相手キャラクターの様子・表情・動き」を説明していないか（主人公の感触のみであるべき）
- [ ] セリフ行に `【 キャラ名 】` ラベルが付いているか（テキストウィンドウ表示の体裁）
- [ ] 地の文 vs セリフ比率が概ね **2:8** になっているか
- [ ] 文字配分が **溜め40% / 結合50% / 余韻10%** の比率を概ね守っているか
- [ ] 行為中セリフに **`っ`** が混在しているか（昂りの表現）
- [ ] 1段落に **触覚系五感ワードが2つ以上** あるか
- [ ] キャラクターの **言語能力の崩壊アーク**（序盤：固有口調 → 終盤：喘ぎのみ）が段階的に表現されているか

### レビュー結果の記録

レビュー後、`workspace/review_log.md` に以下の形式で記録する。

```markdown
## レビュー第[N]回

### 判定: PASS / FAIL

### 合格項目
- [チェックリストの合格項目を列挙]

### 指摘事項（FAILの場合）
| 項目 | 問題点 | 改善指示 |
|------|--------|---------|
| 誘惑ロジック | 第2幕で「いいよ」という合意が発生している | なし崩し的な崩壊に書き換える。理性が抵抗しながら体が反応する矛盾を描写する |
| テンションコントロール | 絶頂シーンの文体が変わっていない | 一文を10文字以内に短く切り、読点を多用すること |
| メタタグ変換漏れ | 「彼女の頬が赤く染まった」等の視覚表現が地の文に残っている | 削除ではなく `[FACE:shame][CG:face_blush_01]` に変換し、地の文はその行の触覚・心理描写に差し替える |
| ラリー不足 | 連続する7本のナレーションブロックがあり会話が途切れている | ダイアログとモノローグを交互に挟み、ラリー形式に組み直す |
```

### リテイクの上限

- **最大3回**までリテイクをかける
- 3回実施してもFAILが続く場合は、ユーザーにレビュー結果を報告して判断を仰ぐ
- PASSの基準：チェックリスト全33項目中、27項目以上が合格（80%以上）
- ただし **F. ゲームメディア原則** の「表情/声/雰囲気のナレーション説明」3項目は**必須合格**（1つでも不合格なら即FAIL）
- **G. 数値的制約** の「セリフ比率3:7」「言語能力崩壊アーク」は準必須（どちらか未達でもFAIL）

---

## Phase 3: 品質確認

scripter の出力後、以下を確認する。

1. ブリーフの「感情アーク」が最終JSONに反映されているか
2. 目標ライン数（100〜120）を満たしているか
3. 画像・音声アセットのファイル参照に欠損がないか

問題があればスクリプターに修正指示を出す。問題なければユーザーに完成を報告する。

---

## Workspace 構造

```
workspace/
  brief.md              ← プロデューサーが作成
  scenario_draft.md     ← シナリオライターが作成（リテイクごとに上書き）
  review_log.md         ← プロデューサーがレビューごとに追記
  cg_manifest.json      ← 演出エンジニアが作成
  audio_manifest.json   ← ボイスデザイナーが作成
```
